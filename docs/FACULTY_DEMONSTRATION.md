## Step 15: Integrity constraints preventing invalid data

Run these one by one. Each **fails**, and that is the point.

```sql
-- (a) UNIQUE: a register number that already exists
INSERT INTO student (student_name, register_number, department, year_of_study, email)
VALUES ('Copy', '24BCE1012', 'CSE', 3, 'copy@students.example.edu');
-- ERROR 1062: Duplicate entry '24BCE1012' for key 'student.uq_student_register_no'

-- (b) FOREIGN KEY: a lab that does not exist
INSERT INTO equipment (equipment_name, serial_number, category_id, lab_id, purchase_id)
VALUES ('Ghost', 'TST-0001', 1, 99, 1);
-- ERROR 1452: Cannot add or update a child row ... fk_equipment_lab

-- (c) CHECK: year of study must be 1-5
INSERT INTO student (student_name, register_number, department, year_of_study, email)
VALUES ('Bad Year', '26BCE1998', 'CSE', 7, 'bad.year@students.example.edu');
-- ERROR 3819: Check constraint 'chk_student_year' is violated.

-- (d) BUSINESS RULE: oscilloscope OSC-DS1-0001 is already issued to Aarav
INSERT INTO equipment_allocation (equipment_id, student_id, staff_id, allocation_date, expected_return_date)
VALUES (1, 10, 1, '2026-10-10', '2026-10-17');
-- ERROR 1062: Duplicate entry '1' for key 'equipment_allocation.uq_allocation_one_active_per_equipment'

-- (e) HISTORY: a student with allocation history cannot be deleted

-- ERROR 1451: Cannot delete or update a parent row ... fk_allocation_student
```

**Say:**
- "The database itself rejects invalid data, whatever program sends it."
- "Rule (d) is a cross-row rule: a CHECK constraint cannot see other rows, so we used a functional UNIQUE index that only covers active allocations."
- "Rule (e) protects history, because we used ON DELETE RESTRICT, not CASCADE."

**Concept:** UNIQUE, FOREIGN KEY, CHECK, referential integrity.

**Say:**

## Viva questions and answers

**1. What is a primary key? Which ones did you use?**
A primary key is a column, or set of columns, that uniquely identifies each row. It cannot be NULL or duplicated. Each table has an integer `AUTO_INCREMENT` key named after the Review 1 key, such as `equipment_id` or `allocation_id`. These are *surrogate* keys: they carry no meaning, so they never need to change.

**2. Then why are register_number and serial_number not primary keys?**
They are *candidate keys*, so we declared them `UNIQUE`. Real-world identifiers can be corrected or reformatted, and a primary key is copied into foreign keys in other tables. A meaningless integer key keeps every relationship stable, while UNIQUE still blocks duplicates.

**3. What is a foreign key?**
A column whose value must match a primary key value in another (parent) table, or be NULL if allowed. Example: `equipment.lab_id` must be an existing `lab.lab_id`. It implements a relationship from the ER diagram and enforces **referential integrity**: no child row can point to a parent that does not exist.

**4. How did you convert the ER diagram into tables?**
- Each entity became a table, and its attributes became columns.
- For each **1:N** relationship, the primary key of the "1" side was added as a foreign key on the "N" side.
- For the **1:1** Allocation–Return relationship, the foreign key went into the return table and was made `UNIQUE`.
- There were no M:N relationships, so no junction tables were needed.

**5. How is a one-to-many relationship different from a one-to-one in SQL?**
Both use a foreign key. In 1:N the foreign key column may repeat: many equipment rows have `lab_id = 4`. In 1:1 the foreign key is also `UNIQUE`, so each parent can appear only once (`equipment_return.allocation_id`).

**6. Why is the foreign key in equipment_return and not in equipment_allocation?**
- A return only exists after the allocation, and not every allocation has one yet.
- If the allocation table held `return_id`, it would be NULL for every outstanding loan and would need an extra UPDATE when the item came back.
- Putting the key in the return table gives optional participation naturally: no return row means not yet returned.

**7. What is referential integrity, and what happens if I delete a student?**
Referential integrity means every foreign key value refers to an existing row. All our foreign keys use `ON DELETE RESTRICT`, so deleting a student who has allocations fails with error 1451. We chose RESTRICT over CASCADE because CASCADE would silently delete the student's allocation and return history, and Review 1 requires full history.

**8. Explain NOT NULL, UNIQUE, CHECK and DEFAULT with examples.**

| Constraint | What it does | Example |
|---|---|---|
| NOT NULL | The value must be present | Every equipment item must have a `lab_id` |
| UNIQUE | No two rows can share the value | `serial_number` |
| CHECK | The value must satisfy a condition | `year_of_study BETWEEN 1 AND 5`; `total_amount > 0`; `expected_return_date >= allocation_date` |
| DEFAULT | Value used when none is given | A new purchase is `'Ordered'`; a new allocation is `'Issued'` |

**9. What is normalization? What normal form is your design in?**
Normalization organises data so that each fact is stored once. This avoids update, insertion and deletion anomalies.
- **1NF:** atomic values and no repeating groups. Each equipment item is its own row, not a list inside the purchase.
- **2NF:** all our primary keys are single columns, so there are no partial dependencies.
- **3NF:** no non-key column depends on another non-key column. For example, we store `lab_id` in equipment, not the lab's location, because location depends on the lab, not on the equipment.

Every determinant in our functional dependencies is a candidate key, so the tables are also in BCNF under the stated assumptions (docs/NORMALIZATION.md).

**10. Give an example of an update anomaly your design avoids.**
In a flat register, the location of the Electronics and Circuits Lab would be repeated in every row for its equipment. Changing it in some rows but not others leaves conflicting data. In our design the location is stored once, in `lab`, and every equipment row finds it through `lab_id`.

**11. Is there any redundancy in your design?**
Yes, deliberate and controlled. `availability_status` and `allocation_status` could be derived from other tables, but they are attributes in the approved ER diagram and are used constantly. They are updated only inside the allocation and return transactions, a CHECK forbids "Damaged and Available", and validation queries V06, V07, V10 and V11 detect any mismatch. Totals and "overdue" are never stored; they are always computed.

**12. What is the difference between WHERE and HAVING?**
- **WHERE** filters individual rows *before* GROUP BY, and cannot use aggregate functions.
- **HAVING** filters groups *after* GROUP BY, and can.

Example (Q24): `WHERE purchase_status <> 'Cancelled'` removes rows first; then `HAVING COUNT(*) > 1 AND SUM(total_amount) > 50000` removes whole supplier groups.

**13. What types of JOIN did you use?**
- **INNER JOIN** returns only matching pairs, e.g. purchases with their supplier.
- **LEFT JOIN** returns every row of the left table, with NULLs where nothing matches. We used it for students including those with zero allocations (Q29), allocations including unreturned ones (Q32), and equipment never maintained (Q34, `WHERE m.maintenance_id IS NULL`).
- **Multi-table joins** of 3–5 tables (Q31, Q36).

**14. How did you avoid duplicate rows in joins?**
- **Child → parent joins** (N:1) never multiply rows.
- **Two independent 1:N children** of the same parent, such as allocations and maintenance of one equipment, would multiply if joined directly: 2 × 2 = 4 rows. Q38 avoids this by aggregating each child in a derived table first and then joining the one-row-per-equipment results.

**15. What is a correlated subquery?**
A subquery that refers to a column of the outer query, so it is evaluated once per outer row. In Q45, `WHERE m2.maintenance_type = m.maintenance_type` makes the inner AVG the average of *that row's* maintenance type. A non-correlated subquery, such as Q39's overall average, is evaluated only once.

**16. EXISTS vs IN?**
- `IN (subquery)` compares a value with the list the subquery returns (Q41).
- `EXISTS (subquery)` is true if the correlated subquery returns at least one row (Q43).
- `NOT IN` returns nothing if the list contains a NULL. `NOT EXISTS` does not have that problem, so it is the safer choice for "has no …" questions (Q44).

**17. What is a view? Does it store data?**
A view is a named, stored SELECT statement, a virtual table. It does not store data: every query on it re-runs the SELECT against the base tables, so it is always current. Views simplify repeated joins (`vw_equipment_inventory`) and can expose only selected rows or columns (`vw_outstanding_allocations`). A view cannot send alerts or run on a schedule.

**18. What is a transaction? Where do you use one?**
A transaction is a group of statements that succeed or fail together. It has the ACID properties: Atomicity, Consistency, Isolation, Durability.
- **Allocation** inserts the allocation *and* marks the equipment Allocated.
- **Return** inserts the return, closes the allocation, *and* updates the equipment.

`sp_allocate_equipment` and `sp_return_equipment` wrap these steps in `START TRANSACTION … COMMIT`, and on any error they `ROLLBACK`. The sample data script also loads everything in one transaction.

**19. How do you stop two staff members issuing the same item to two students at the same time?**
At three levels:
1. **Functional UNIQUE index.** It covers only active ("Issued") allocations, so at most one can exist per equipment item. Being a unique index, it also works when two transactions insert at the same moment: the second waits and then fails with error 1062. Test TC54 proves this.
2. **Row locking in the procedure.** The allocation procedure locks the equipment row with `SELECT … FOR UPDATE`. A concurrent request waits, then sees "Allocated" and is refused (TC53).
3. **Audit queries.** V08 and V09 detect any conflicting or overlapping allocations in the history.

A plain CHECK constraint cannot do this, because it only sees one row.

**20. Why keep allocation history instead of just updating the equipment?**
- Review 1 requires usage history and accountability: who had which item, when, who issued it, and in what condition it came back.
- If we only stored the current borrower in `equipment`, every new allocation would overwrite the previous one.
- With a separate row per allocation, we can answer questions like "which students return late?" (Q37) or "how often is this item used?" (Q38).

**21. What does "consistency" mean for your database?**
The data always obeys the rules: keys, foreign keys, CHECK constraints and business rules.
- **Constraints** guarantee the per-row and per-relationship rules automatically.
- **Transactions** guarantee that multi-table changes are never half done.
- **The validation script** (`09`) checks the cross-table rules and finds zero violations on the sample data.

**22. Why DECIMAL and not FLOAT for money?**
FLOAT is binary floating point: values such as 0.10 cannot be stored exactly, and sums drift. `DECIMAL(12,2)` stores exact values with 2 decimal places, which is what money needs.

**23. Why is "Condition" called equipment_condition?**
`CONDITION` is a reserved word in MySQL. A column named `condition` would cause syntax errors unless it was quoted everywhere. `Year` became `year_of_study` for the same kind of reason (DESIGN_DECISIONS D-02).
